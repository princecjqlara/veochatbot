# Six-Page chatbot setup

The enabled Pages are Manawari Studios, Loki Media, Vista Media Agency, Onset Media Agency, SAMA KANA MEDIA, and Azshinari. Every chatbot configuration field matches Azshinari, excluding row IDs, Page IDs, and creation/update timestamps. All six explicitly use Azshinari's shared knowledge library, with 478 ready documents. Page identities and customer conversation histories remain Page-specific.

The same model, instructions, fallback, intake fields, completion target, reply splitting, stop rules, and first-day follow-up settings apply to all six. Trial mode is disabled. The day 2–7 schedule is empty on all six because Meta was rejecting `HUMAN_AGENT` sends without approval. 804 pending/processing/manual follow-up jobs using that tag were cancelled. Existing failure records are retained; they are historical evidence, not erased. Original settings and affected jobs are backed up locally before the changes.

Onset and Azshinari use the Barra Meta app, whose callback already targets the chatbot. The other four use the Tokko Meta app, whose original callback targets an application without the AI chatbot. The new `/api/facebook/partner-webhook` route verifies the Tokko app signature and splits each Page batch by an explicit Facebook Page ID allowlist. Selected entries enter the existing chatbot handler, using an internally signed request. Other entries retain their complete messaging, standby, and change data and are forwarded with the Tokko signature to the original callback. Routing errors return HTTP 503 so Meta can retry. Primary signature validation and chatbot reply idempotency remain in effect.

The dispatcher uses `FACEBOOK_PARTNER_APP_SECRET`, `FACEBOOK_PARTNER_CHATBOT_PAGE_IDS`, and `FACEBOOK_PARTNER_LEGACY_WEBHOOK_URL`. The Tokko app's Page callback is connected to this route only after production verification passes. Its subscribed fields and other object callbacks are preserved. Pages outside the allowlist continue to use their original application; their webhook delivery now passes through this dispatcher and therefore also depends on its availability. Both app callbacks and all Page subscriptions are backed up before mutation.

All six Page subscriptions include `messages`, `messaging_postbacks`, and `message_echoes`, so human replies can trigger existing handoff protection. All six tokens are valid and have `pages_messaging` and `pages_manage_metadata`; live Messenger conversation reads succeed.

Validation: 502 tests in 74 files pass, including signed partner routing, mixed Page batches, legacy preservation, invalid signatures, and retry behavior. TypeScript and targeted ESLint checks pass. The production build succeeds with pre-existing dashboard lint warnings. Each Page passes a production reply preview and follow-up preview with retrieved knowledge and media, with no generation or retrieval warnings. These previews do not send Messenger messages. Empty signed webhook probes and Page entries without customer events verify production routing without modifying contacts or sending messages. Organic customer delivery is separate from these probes; token validity and passing previews do not guarantee that Meta will deliver every future message.

Audit artifacts and rollback backups are in the parent workspace's ignored `data/enable-six-pages-*` files. Secret values are excluded from reports. Do not include trailing newlines when supplying secret values to `vercel env add` through stdin.
